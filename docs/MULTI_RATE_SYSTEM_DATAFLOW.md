## 🎯 关键设计决策

### 为什么是 100 Hz？

1. **相机瓶颈**: 30 Hz 太慢，会导致动作抽搐
2. **API 限制**: `move_joint()` 延迟 10ms，理论上限 100 Hz
3. **计算开销**: 100 Hz 时 Python 代码有 10ms 执行时间，足够
4. **性价比**: 更高频率（如 500 Hz）收益递减，但 CPU 负担增加

### 为什么需要 Kalman Filter？

**问题**: 相机只有 30 Hz，但控制需要 100 Hz

**解决**: Kalman Filter 的 Predict 步骤

```python
# 伪代码
while True:  # 100 Hz 循环
    # 1. 总是预测（即使没有新图像）
    kf.predict(dt=0.01)  # 使用上次速度估计下一步

    # 2. 只有新图像到达时才更新
    if new_image_available:
        kf.update(measurement)

    # 3. 使用预测/更新后的状态
    q_cmd = kf.get_state()
    robot.send_command(q_cmd)

    time.sleep(0.01)  # 维持 100 Hz
```

**效果**:
- 30 Hz 图像 → 100 Hz 平滑轨迹
- 避免"抽搐"现象
- 自然的运动插值

```python
class RateTracker:
    """简单的频率计"""
    def __init__(self):
        self.last_time = time.time()

    def tick(self) -> float:
        now = time.time()
        dt = now - self.last_time
        freq = 1.0 / dt if dt > 0 else 0
        self.last_time = now
        return freq

# 使用
vision_rate = RateTracker()
control_rate = RateTracker()

# 在循环中
print(f"Vision: {vision_rate.tick():.1f} Hz")
print(f"Control: {control_rate.tick():.1f} Hz")
```

## ⚠️ 常见问题

### Q1: 为什么 Control Thread 频率不稳定？

**可能原因**:
1. **被 Vision Thread 阻塞** - 没有使用多线程
2. **计算太慢** - VIST 算法超过 10ms
3. **GIL 限制** - Python 全局解释器锁

**解决方案**:
- ✅ 使用多线程（已实现）
- ✅ 优化算法（减少不必要的计算）
- ⚠️ 考虑 C++ 扩展（如果 Python 不够快）

### Q2: 为什么不能直接提高到 1000 Hz？

**限制因素**:
1. **API 延迟**: `move_joint()` 需要 10ms，理论上限 100 Hz
2. **Python GIL**: 限制真正的并行
3. **计算开销**: VIST 算法需要时间

**如果需要更高频率**:
- 使用 `joint_follow()` API（但有 bug，不推荐）
- 用 C++ 重写核心算法
- 使用实时操作系统（RTOS）

### Q3: 相机能否提高到 60 Hz？

**可以，但**:
- 需要降低分辨率（如 640x480 → 320x240）
- 可能影响检测精度
- 对于遥操作，30 Hz 通常足够
